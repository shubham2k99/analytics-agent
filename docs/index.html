GAnalyst

Objective

As a marketing analyst, GA4's interface is familiar territory — but pulling a specific number for a specific stakeholder question usually means navigating several report screens, adjusting date ranges, and exporting to a spreadsheet before it's presentable. The goal was to collapse that into a single question typed in plain English.

The second, equally important goal: build real, defensible AI-engineering literacy — not by reading about how agents work, but by making every decision that determines whether one works correctly. Which tools does the agent get access to. What happens when a tool call fails. How do you know if an answer is actually right. Those are the questions this project was built to answer firsthand.

How it started

The starting brief was simple to state and non-trivial to build: a chat interface, backed by a real GA4 connection via OAuth (not a hardcoded service account — the goal was something that could eventually be shared with other people, each seeing their own data), that could answer traffic questions and render charts inline.

The scope was deliberately a full web application rather than a script or notebook. A script proves an API call works; a web app proves an entire system holds together — auth, session handling, an LLM in the loop, and a UI a non-technical person could actually use.

Architecture

Three parts talk to each other, with the backend as the only component that ever touches credentials:

Browser (chat UI) ↕ Next.js backend — API routes + encrypted session cookie ↕ ↕ Google (OAuth + GA4 Data API) Claude API (tool use)

The core mechanism is Claude's tool use (function calling). Rather than letting the model generate a GA4 query as free text, it's given three narrowly scoped tools:

list_ga4_properties

Lists the GA4 properties the connected Google account can access.

run_ga4_report

Executes a real GA4 Data API report — takes exact metric names, dimension names, and a date range, nothing more open-ended than that.

propose_chart

Packages a subset of the fetched data into a chart spec (type, axes, series) for the frontend to render with Recharts.

When a question comes in, the backend sends it to Claude along with these tool definitions. Claude doesn't fetch anything itself — it returns a structured request (e.g. run_ga4_report({ metrics: ["sessions"], dimensions: ["date"], ... })), the backend executes the actual HTTPS call to Google, and the real result is fed back to Claude to reason over. This loop can repeat several times in a single turn — a comparison question might trigger two separate report calls before Claude has enough to write an answer — capped at 6 iterations to prevent runaway loops.

Session state (the Google OAuth tokens, which GA4 property is selected) lives in an encrypted cookie via iron-session, not a database — a deliberate scope decision for a single-user MVP, with the tradeoff noted explicitly for anyone scaling this to multiple concurrent users.

Build workflow

The build moved in five stages, each with a distinct failure mode to solve:

  1. Scaffolding. Next.js App Router project, GA4 Data API client (thin wrapper around runReport and accountSummaries), and the Claude tool-use agent loop — built and build-verified before ever touching a real Google Cloud project, to isolate code correctness from environment setup.
  2. Google Cloud + credentials. OAuth client, consent screen scopes (analytics.readonly), test users, and an Anthropic API key. This stage surfaced more real friction than any code — see the bug log below.
  3. The session bug. A working-looking OAuth flow that silently failed to persist login state, diagnosed from server logs and fixed by switching cookie-handling APIs entirely (detailed below).
  4. Visual identity. Deliberately moved off default Tailwind styling toward a "measurement instrument" aesthetic — paper background, brass accent, Fraunces for display type, IBM Plex Mono for all numeric/data readouts — reasoning that a tool about precise numbers should look like one.
  5. Hardening and validation. Cross-checking agent answers against the live GA4 dashboard, understanding GA4's own quirks (sampling, thresholding, a globally shared quota on the public demo property) well enough to distinguish "the agent is wrong" from "GA4 itself is behaving as designed."

Bugs that shaped the build

None of these were exotic — they were the ordinary friction of shipping something real, and each one taught something that a tutorial skips.

The OAuth login loop

After a successful Google login, the app would redirect home — then immediately act as if login had never happened, sending the user back to "Connect." The session cookie was being set using an older getIronSession(req, res, ...) pattern built for Node's raw request/response objects, which doesn't reliably persist cookies against Next.js's App Router Request/Response objects. The fix: rewrite every session read/write to use getIronSession(await cookies(), ...) from next/headers — the API the App Router actually expects. Diagnosed by reading raw server request logs and noticing the callback route fired twice in a row, which is the visible symptom of a session that never actually saved.

A leaked API key, caught and rotated

Midway through adding a new feature, a routine check of the GitHub repo revealed .env.local — containing the real Anthropic key, Google OAuth secret, and session secret — sitting in the public commit history. Root cause: a missing .gitignore file. All three credentials were rotated immediately, the repository was deleted and rebuilt from a clean local state with .gitignore verified before the first commit, and every subsequent commit was checked for file count and content before publishing. The practical lesson: treat "check the actual file list before you commit" as a non-negotiable step, not a nice-to-have.

Silent key corruption via a rich-text editor

A pasted API key produced a persistent "invalid API key" error even though the key was copied correctly. The cause: pasting into TextEdit's default rich-text mode subtly altered characters in a way that was visually invisible but broke the literal string. Fixed by writing the key directly from the clipboard into the env file via a terminal command (sed + pbpaste), bypassing any GUI text editor entirely.

A duplicate env variable, silently ignored

Even after "fixing" the API key, the same auth error persisted. A placeholder line (ANTHROPIC_API_KEY=letter) had been left in the file alongside the real key on a separate line — and the environment loader kept the first declared value, silently discarding the second. Diagnosed by checking the byte length of the matched line before assuming the key itself was wrong.

Validating the agent's answers

A working pipeline and a trustworthy one are different claims. Getting the agent to respond isn't evidence it's responding correctly — GA4 has real limits (sampling on complex queries, thresholding that hides small user counts, a default attribution model that may not match how a team actually reports) that an LLM can easily paper over with a confident-sounding but wrong answer.

The approach taken here, in order of how much it actually helps:

  • A golden set. A fixed list of real questions with answers cross-checked directly against the native GA4 dashboard, re-run after any change to the system prompt or agent logic.
  • Groundedness checks. Confirming the final written answer actually matches the raw numbers the tool call returned, not a loosely-summarized approximation of them.
  • Explicit guardrails in the system prompt. Instructions that constrain the model to real GA4 metric names and require a tool call before any numeric claim — closing off the easiest path to a hallucinated statistic.

Final outcome

A working chat interface, connectable to any GA4 property via OAuth (including Google's public demo account, so it's testable without needing your own site), that answers real traffic questions using live fetched data and renders inline charts — plus a rebuilt visual identity, an in-app project explainer, and a clean, secret-free public repository ready to deploy to Vercel as a live, shareable app.

Learnings

Tool design determines agent reliability more than the model choice does

Narrow, specific tools (fetch exactly this report) produce predictable behavior. Broad or vague tools invite the model to guess.

AI answers need active validation, not trust by default

A golden set and a groundedness habit are the actual difference between a demo and something you'd let a stakeholder rely on.

Most real bugs in a build like this are environment issues, not logic bugs

Disk space, a missing gitignore, a text editor silently altering a paste — none of these show up in a tutorial, and all of them cost more debugging time than any actual application code.

Knowing when not to use an LLM is part of using one well

Fixed, known metrics don't need an agent in the loop at all — a direct API call is faster, cheaper, and has nothing to hallucinate. The chat only earns its keep for genuinely open-ended questions.
