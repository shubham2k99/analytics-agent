Objective & motivation

As a marketing analyst, the actual bottleneck was never understanding GA4 — it was the friction of getting a specific number in front of a specific stakeholder. A simple question like "what drove last week's traffic spike?" usually meant navigating three report screens, adjusting a date range, cross-referencing a channel breakdown, and exporting to a spreadsheet before it was presentable. That's real time, repeated constantly, for questions that are conceptually simple.

The business case for this project was collapsing that entire loop into one typed question. Instead of "let me pull that report and get back to you," the goal was "ask, and get a real, data-grounded answer in seconds" — genuinely useful for ad hoc stakeholder requests, standups, or a quick sanity check before a meeting.

The second motivation was personal and just as important: building real, defensible AI-engineering literacy rather than reading about it. Every decision that determines whether an AI agent actually works — what tools it's allowed to use, what happens when something fails, how you know an answer is trustworthy — had to be made here, not assumed.

Project walkthrough

01Scaffolding. Started with a Next.js App Router project, a thin GA4 Data API client (wrapping runReport and accountSummaries), and a Claude tool-use agent loop — built and build-verified before ever touching a real Google Cloud project, to separate code correctness from environment setup.

02Google Cloud credentials. Created an OAuth client, enabled the GA4 Data + Admin APIs, set the analytics.readonly scope on the consent screen, and added test users.

Practical tip: for the Anthropic API key, a $5 credit is genuinely enough to build and thoroughly test something like this — each question costs fractions of a cent, and $5 covers far more testing than you'd expect before you need to think about billing again.

03Wiring the agent loop. The core mechanism is Claude's tool use: rather than letting the model generate a GA4 query as free text, it's given three narrow tools — list_ga4_properties, run_ga4_report (exact metrics, dimensions, date range — nothing looser), and propose_chart. Claude requests a tool call, the backend executes the real API request, and the result is fed back for Claude to reason over — repeating up to 6 times per question before it writes a final answer.

04The session bug. A working-looking OAuth flow silently failed to persist login — traced to an outdated cookie-handling pattern that doesn't reliably work with the Next.js App Router, fixed by switching to the next/headers cookies API (full detail in the problems log below).

05Visual identity. Moved off default styling toward a deliberate "measurement instrument" look — paper background, brass accent, serif display type, monospace data readouts — reasoning that a tool about precise numbers should visually read like one.

06Validation and hardening. Cross-checked agent answers against the live GA4 dashboard, built a small "golden set" of test questions with known answers, and added an explicit instruction requiring every answer to close with a grounded suggestion for what to look into next.

07Going live. Cleaned the repo of secrets (see the leaked-key incident below), deployed to Vercel, and added a bring-your-own-key flow so a public visitor's usage is billed to their own Anthropic account, never mine.

Output

A working chat interface, connectable to any GA4 property via OAuth — including Google's public demo account, so it's testable without needing a real site — that answers genuine traffic questions using live fetched data, renders inline charts, and closes every answer with a suggested next step. It's deployed, publicly linkable, and the underlying agent logic is designed to keep improving without changing the front end visitors interact with.

Learnings

Tool design determines agent reliability more than the model choice does

Narrow, specific tools (fetch exactly this report) produce predictable behavior. Broad or vague tools invite the model to guess.

"It responds" and "it's right" are different claims

A golden set and a habit of checking groundedness are the actual difference between a demo and something you'd let a stakeholder rely on.

Most real bugs are environment issues, not logic bugs

Disk space, a missing gitignore, a text editor silently altering a paste — none of these show up in a tutorial, and all of them cost more time than any actual application code.

Knowing when not to use an LLM is part of using one well

Fixed, known metrics don't need an agent in the loop — a direct API call is faster, cheaper, and has nothing to hallucinate. The chat only earns its keep for genuinely open-ended questions.

Major problems & errors

None of these were exotic — they were the ordinary friction of shipping something real, and each one taught something a tutorial skips.

The OAuth login loop

After a successful Google login, the app redirected home, then acted as if login never happened. Root cause: session cookies were being set with an older getIronSession(req, res, ...) pattern that doesn't reliably persist against the App Router's Request/Response objects. Fixed by rewriting every session read/write to use getIronSession(await cookies(), ...) from next/headers.

A leaked API key, caught and rotated

A routine check of the GitHub repo revealed .env.local — real Anthropic key, Google OAuth secret, session secret — sitting in public commit history, caused by a missing .gitignore. All three credentials were rotated immediately, and the repository was deleted and rebuilt clean, with the file list checked before every commit from that point on.

Silent key corruption via a rich-text editor

A correctly-copied API key still produced "invalid API key" errors. Cause: pasting into a rich-text editor subtly altered characters in a way that was visually invisible but broke the literal string. Fixed by writing the key directly from the clipboard into the env file via terminal, bypassing any GUI editor entirely.

A duplicate env variable, silently ignored

Even after "fixing" the key, the same error persisted. A placeholder line had been left in the file alongside the real key on a separate line, and the environment loader silently kept the first declared value. Diagnosed by checking the byte length of the matched line before assuming the key itself was wrong.
